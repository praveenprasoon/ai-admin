01 · The case for change

Our constraint is not just coding speed.
It is the whole delivery system.

Today’s SDLC gives us planning and tracking. ADLC should connect intent → knowledge → execution → proof → production learning.

Fragmented intent

Requirements lose context

Business asks, Jira Stories, architecture decisions, acceptance criteria and actual tests can drift apart across teams.

Knowledge risk

Rules are scattered

Critical policy, configuration, formulas, schemas and system behavior live across documents, repositories and experts.

Late discovery

Integration and defects surface late

Local task completion does not prove end-to-end business correctness, data reconciliation or production safety.

Measurement gap

Activity is easier to count than value

Raw story points, generated code and agent sessions can miss review burden, hidden rework and escaped defects.

Problem statement to validateWe lack one consistently enforced, evidence-backed path from approved business intent through system implementation to verified production outcomes. The pilot will establish the baseline and show where the largest avoidable delay, rework and risk actually occur.

04A · Harness design

The harness is the safety contract at every phase—not just coding.

Every phase receives controlled context, explicit permissions, measurable limits, a structured output contract and a rule for when to stop or escalate.

Knowledge harness

Source allowlist, ACL-aware retrieval, freshness/version rules, provenance, source ranking and injection-resistant handling.

Output: cited context pack

Specification / Story harness

Approved templates, completeness checks, ambiguity handling, rule references, Jira field contract and duplicate prevention.

Output: traceable draft

Plan / task harness

Dependency discovery, task boundaries, repo ownership, technology-pack selection, sequencing and scope limits.

Output: task DAG

Agent execution harness

Isolated workspace, least-privilege tools, approved model/context, time and cost budgets, bounded loops and structured outputs.

Output: diff + run trace

Test / evaluation harness

Independent oracles, deterministic gate checks, domain regression packs, evidence-to-commit binding and must-pass policies.

Output: verified evidence

Release / learning harness

Human approval state, environment guard, rollback plan, post-deploy reconciliation, candidate knowledge updates and canary/rollback.

Output: signed decision + telemetry
Agent harness

Constrains an invocation

What it can see, which tools it can call, what it may change, how long it can run and what evidence it must return.

Workflow orchestrator

Coordinates the lifecycle

Tracks durable state, task dependencies, retries, concurrency, approvals, escalation and the next allowed transition.

Policy / gate engine

Evaluates evidence

Allows progression only when mandatory conditions are satisfied; a generated “pass” statement is never sufficient.

Enterprise harness contractInput context + allowed actions + output schema + evidence requirements + limits + stop conditions + responsible approver. Reuse this contract across teams; specialize the rules for each domain, system and risk tier.

06 · Domain proof point 1
HCM configuration · Example change path

Oracle HCM + Fast Formula business logic

Complex eligibility, calculations, effective dating, payroll/benefit dependencies and configuration-specific behavior.

Illustrative business request

“Update an eligibility rule for a future effective date without changing existing employee outcomes.”

ADLC discovers the approved rule, current formula and dependencies; it turns the desired change into explicit behavior and generates a controlled, testable implementation package.

AC-01 · Effective date

Before the approved effective date, existing rule outcomes remain unchanged; on/after the date, the approved new rule applies.

AC-02 · Eligibility boundaries

Approved examples cover eligible, ineligible and boundary cases; the result matches the functional owner's expected outcome.

AC-03 · Regression

Unrelated populations / formula paths remain unchanged across the approved regression cohort.

AC-04 · Audit + rollback

Formula/config version, approvals and environment promotion are traceable; recovery follows the approved runbook.

Context pack

What is retrieved

Approved policy and effective date · formula and configuration version · relevant HCM setup · upstream/downstream dependencies · functional examples · prior incidents / accepted test cases.

Control points

What must be proven

  • Formula syntax and supported constructs validated in the actual toolchain
  • Expected outcomes independently confirmed by the functional owner
  • Positive, negative, boundary and effective-dated regression tests executed
  • Configuration diff reviewed; environment and promotion controls enforced
  • Post-promotion verification and operational handover recorded
Human gateThe functional/business owner approves business meaning and expected calculations; the HCM/configuration owner approves technical change and promotion; production authority decides release. No generated formula is trusted just because it compiles.

11 · A system that gets better safely

Learning is a governed release process,
not a model rewriting its own rules.

OBSERVE

Capture failures

Unsupported claims, rule conflict, missed test, human correction, CI failure, production defect or reconciliation variance.

DIAGNOSE

Fix the right layer

Approved source, knowledge retrieval, spec template, task prompt, test pack, classifier, orchestrator or telemetry.

EVALUATE

Replay and canary

Golden-set questions, negative access tests, regression suites, contract checks and domain-specific fixtures.

PROMOTE

Version or rollback

Promote only after gate evidence; preserve source history and last-known-good; reverse failed candidates.

Knowledge accuracy / grounding

Measure by domain and risk

  • Golden-set answer correctness with evidence support
  • Claim-to-source coverage and citation validity
  • Freshness/effective-date correctness and contradiction rate
  • Authorization leakage tests: zero tolerated for restricted data
  • Critical must-pass rules tested separately from aggregate score
Proposed promotion policy

Use a threshold plus hard stops

For initial experiments, an aggregate 90% golden-set floor may be a proposed minimum for promotion; critical business rules must pass every designated must-pass test. The right threshold must be calibrated with owners, sample coverage and risk. A 90% score is not a claim of production safety.

14 · Risk is part of the design

The main failure modes are known categories.
We make them testable and owned.

Knowledge + intent

Stale source or invented rule

Use source owner/version/effective date, claim traceability, rule conflict detection and owner clarification. Unsupported material claims block readiness.

Quality independence

Agent writes its own false proof

Use independent expected results, QA-reviewed oracle fixtures, negative cases and production reconciliation—not tests designed only to confirm generated behavior.

Security + data

Privilege or data leakage

Authorize before retrieval/tool use, isolate environments, redact sensitive telemetry and test prompt-injection and access-deny scenarios.

Cross-system delivery

Hidden dependency or contract drift

Maintain linked parent/child specs, versioned contracts, dependency DAG, compatibility tests and end-to-end validation.

Reliability

Duplicate retries or endless loops

Durable workflow state, idempotency keys, bounded tool/model budgets, timeouts, dead-letter handling and replay tests.

Measurement

Productivity appears better than reality

Include human review, context repair, rework, CI and tool cost; use comparable work, matched controls, confidence and quality guardrails.

Open assumptions need ownersBefore scale, validate the actual source hierarchy, critical rule sets, system ownership/lineage, permission model, acceptance-test oracles, human-effort capture and production recovery procedures. If a control cannot be evidenced, narrow the automation rather than waive the control.
15A · Questions executives will ask

Frequently asked questions.
Credibility is part of the control design.

Will agents change existing business rules without approval?

They must not. Rule and design claims are tied to approved, versioned sources. Conflict, missing authority or requested deviation becomes a clarification/decision item and holds affected work. Human approval remains required for material business changes.

What if the knowledge base is stale or wrong?

Measure grounding by domain against reviewed golden sets, test citations and effective dates, check source freshness and permissions, keep the last-known-good version and hold failed candidates. A failing domain moves to assisted mode until evidence passes.

How can we trust tests written by an AI agent?

Do not rely on agent-authored tests alone. Acceptance expected-results come from the business/functional owner; independent test packs and deterministic checks validate the exact commit; critical domains require domain-specific regression and reconciliation evidence.

What happens when an agent, model, tool or CI pipeline fails?

The workflow persists state, uses bounded retries and idempotency keys, records the failure and cost, escalates after limits, and resumes or rolls back under policy. A timeout is not a pass, and a failed mandatory gate cannot be silently bypassed.

Could payroll, HCM or infrastructure changes be released autonomously?

Autonomy is scoped by risk, action and environment. Critical calculations, sensitive data, high-impact cloud changes, exceptions and production releases retain authorized human decision gates. Low-risk reversible tasks may earn more autonomy only after repeatable evidence.

How do we measure real productivity instead of AI activity?

Compare accepted outcomes, active human hours per accepted change, P50/P85 cycle time, first-pass correctness, escaped defects, change failures and full model/tool/CI/review/rework cost. Use a same-team baseline and matched controls where feasible; never compare story points across teams as a common currency.

Does faster delivery mean fewer people are needed?

No such assumption is built into this proposal. First verify capacity released after all review, supervision and rework. Track how those hours are redeployed to business features, deeper testing, resilience, architecture and reducing operational toil. Count cash savings only if actually realized.

Why not adopt BMAD or buy a full platform now?

Spec Kit is the proposed starting SDD contract, not an irreversible bet. Benchmark Spec Kit and BMAD on the same HCM and ETL use cases and compare quality, traceability, onboarding, maintainability, governance integration and total cost. Reuse existing Jira, Git and CI/CD first; buy or extend only where a proven gap remains.

How can this scale across 100+ repositories?

Use shared ingestion metadata and standards with per-repository ownership, access controls, source versions and domain-specific evaluations. Build cross-repo dependency links and task-specific context packs instead of putting all source material into one unrestricted prompt or index.

What proof is required before expanding the pilot?

Pre-agreed baseline, sample size and observation window; measurable improvement in effort or accepted delivery; stable or better security, defect and reconciliation outcomes; verified provenance and human approvals; and positive net value after platform, enablement and governance costs.
