01 / The story

Why this model exists

Today, business rules, architecture decisions, source code, Jira stories, test evidence and operational lessons are spread across tools and repositories. Agents can accelerate work—but only if they receive the right context and cannot bypass the controls that make delivery safe.

Before: context is fragmented

Each team reconstructs rules from old stories, code, wiki pages, tickets and individual memory. Cross-repo changes are easy to miss, and the same context gets pasted into prompts repeatedly.

Intervention: governed context

A project manifest resolves the right repos, approved domain knowledge, contracts, defects and tests. Feature-specific context is version-pinned and loaded only when relevant.

After: evidence-led delivery

Every feature carries traceability from intent through PRs, CI, approvals, release and outcomes. Telemetry is correlated, and lessons become proposed—not automatic—knowledge updates.

02 / System design

Four layers, deliberately separated

Keep common policy reusable, project intent local to its bounded context, implementation in existing repos, and evidence in the tools that actually produce it.

Layer 1

SDD platform

  • Lifecycle templates and skills
  • Gate definitions and schemas
  • Telemetry contract
  • Policy / version compatibility

Shared platform repo

Layer 2

Domain knowledge packs

  • Payroll / compensation rules
  • AWS data and security patterns
  • HCM / PeopleSoft domain guidance
  • Approved reusable contracts

Owned by domain authorities

Layer 3

Project knowledge

  • Project manifest + repo map
  • Architecture / contracts / NFRs
  • Feature specs and dependencies
  • Defect watch + release evidence index

One repo per bounded product

Layer 4

Implementation + evidence

  • React / API / Glue / TFE / SQL
  • HCM configuration artifacts
  • Tests, scans, CI and deployment
  • Jira / Jira Align source links

Native source systems remain authoritative

Non-negotiable: the knowledge UI is a governed view and workflow—not a new place to copy all code, duplicate Jira work items, or silently rewrite business rules. Markdown in version control is the canonical authored knowledge; search indexes and dashboards are derived views.

Project knowledge is an index plus approved intent

It holds the product-specific rules and contracts that teams need to agree on, plus references to implementation and evidence. It does not become a mirror of every implementation repo.

  • project.yaml: repo URLs, owners, default branches, pinned knowledge packs, gate profile and system IDs.
  • knowledge/: reviewed, versioned business semantics, architecture, contracts, invariants, NFRs and known defect warnings.
  • features/: a feature overlay, dependency map and evidence links; not a new authoritative baseline for other teams.
  • proposals/: proposed changes waiting for the right approver—not automatically published truth.

The related repositories stay separate

Shared

sdd-platform/

Core lifecycle, spec templates, agent skills, gate contracts, policy checks, telemetry event schema and knowledge publishing rules.

Domain-owned

domain-payroll/ · domain-aws/

Approved reusable domain guidance. Pin a version or commit so a feature’s assumptions remain reproducible.

Existing code

espp-react/ · api/ · glue/ · liquibase/ · tfe/

Application code, tests, migrations and infrastructure remain in their current repos, with PRs and CI evidence linked by feature ID.

05 / Change control

Two update flows, one governed baseline

Engineering discovery and business-led changes converge on the same review and publication controls. No agent should be able to promote its own inference into an approved domain rule.

Engineering-driven
1 · Feature specPin baseline and map impacted repos
2 · Implement + testLinked PRs; CI produces evidence
3 · Compare behaviorDetect changed contracts / invariants
4 · Propose KB deltaDiff + evidence + affected IDs
5 · Review + publishAuthorized owner approves
Business-driven
1 · PO intakeOutcome, policy change, effective date
2 · Retrieve contextExisting rules, defects, contracts, Jira
3 · Clarify gapsAssumptions and edge cases surfaced
4 · Approve intentBusiness owner confirms semantics
5 · Create spec / storiesJira links and gates are attached
Production defect
1 · QuarantineObserved behavior is not assumed correct
2 · Link impactRule IDs, features, releases and data
3 · ReproduceRegression test + expected behavior
4 · Remediate / exceptionOwner authorizes fix or time-bound risk
5 · Verify + learnProduction evidence then reviewed update
Knowledge refresh
1 · Detect changeBaseline, contract or dependency moves
2 · Impact graphFind only intersecting active features
3 · Classify statusCurrent / revalidate / blocked / superseded
4 · RevalidateTargeted review and tests
5 · Re-pin baselineMerge/release checks confirm freshness
Parallel development rule: each feature works against a pinned baseline and keeps proposed changes in its own overlay. A merge or release checks whether relevant dependencies changed. Only affected work is revalidated; a conflict or critical defect can block a feature. Unrelated features do not need to reload the entire knowledge base.

07 / Guardrails

Defect quarantine prevents false learning

Observed production behavior is evidence of what happened, not proof of what should happen. Record expected vs observed behavior, affected rule IDs, severity, reproduction, regression test and remediation status. Keep the record; never overwrite the approved rule without review.

Staleness and conflict checks

Before merge and release, compare the feature’s pinned baseline with current relevant dependencies. Mark work CURRENT, REVALIDATION_REQUIRED, BLOCKED_BY_CONFLICT or SUPERSEDED. High-risk unresolved defects block unless an authorized, time-bound exception is recorded.

08 / Across project types

One operating model, different risk profiles

The framework stays consistent; the knowledge packs, artifacts and mandatory controls vary by project. Select a scenario to see what belongs in knowledge versus implementation.

ESPP compensation hub

Cross-stack feature: compensation rule change from UI through API, config/data, pipeline and infrastructure.

  • Knowledge: eligibility, calculation semantics, effective dates, API/data contracts, invariants and reconciliation expectations.
  • Repos: React, API, config/DynamoDB, Glue, Liquibase, Terraform.
  • Gates: calculation examples, contract compatibility, migration safety, security, regression and release reconciliation.
  • Telemetry: one feature trace correlates every repo PR and CI run with tokens, cost, elapsed time and human review.

Oracle HCM time-card configuration

Managed configuration and business semantics matter as much as application code.

  • Knowledge: approved time rules, effective-date behavior, schedule exceptions, payroll dependencies and audit requirements.
  • Artifacts: configuration exports/version history, deployment packages, integration repos and test evidence; do not assume every artifact is Git-managed.
  • Gates: domain owner approval, representative time-card cases, payroll impact, audit trail and rollback/restore strategy.
  • Control: observed configuration does not automatically define approved policy; confirm it with the authorized business owner.

PeopleSoft pension / 401k

Legacy financial processing requires high assurance and explicit historical-result validation.

  • Knowledge: rule references, interface maps, data lineage, batch dependencies, cutoff windows and reconciliation controls.
  • Artifacts: PeopleSoft config / code or managed deployment package, interface repos, SQL/batch artifacts, vendor files and runbooks.
  • Gates: historical regression, financial calculation comparison, control totals, security review, business sign-off and operational recovery.
  • Control: a legacy defect is recorded and tested—not promoted into the rulebook simply because it has existed for years.

09 / Challenges and controls

How the model addresses known failure modes

This is not “add an agent and hope.” Each recurring issue has a design control, a system-enforced check and an accountable owner.

Canonical, layered knowledgeShared core + versioned domain packs + project baseline; local repos retain implementation docs.
Parallel teams use stale assumptionsA feature merges against a changed contract or rule.

Adoption sequence

1. Pilot one cross-stack feature with meaningful dependencies. 2. Capture current-state baselines and define metric denominators. 3. Exercise the defect and stale-knowledge paths deliberately. 4. Run a second, higher-risk legacy/batch scenario. 5. Expand only when quality, adoption and operating effort are measured.

What success should mean

Higher goal success and tool-call accuracy; lower avoidable rework and cycle time; reliable security/test gate adherence; lower escaped-defect and change-failure rates; measured token/cost efficiency; acceptable human review effort; and knowledge that remains fresh and owned.
